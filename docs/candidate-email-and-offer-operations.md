# 候选人邮件与 Offer 运维手册

## 上线前配置

1. 在部署环境设置独立的 `EMAIL_ENCRYPTION_KEY`。它必须是 32 字节 padded base64url 密钥，不能与联系人、LLM 或飞书密钥复用。
2. 将 `OFFER_PUBLIC_BASE_URL` 设置为候选人实际访问的站点 origin，例如 `https://recruiting.example.com`。生产环境必须使用 HTTPS，且不能带路径、查询参数或账号信息。
3. 根据企业邮件策略设置 `EMAIL_FROM_ADDRESS`、`EMAIL_FROM_NAME` 和 `EMAIL_SMTP_TIMEOUT_SECONDS`。
4. 系统管理员在网页的邮件设置中填写 SMTP 主机、端口、连接加密方式、账号、密码及回复地址，保存后执行连接测试。服务商标注 SSL/SMTPS 时选择“SSL/TLS（连接即加密）”；标注 STARTTLS 时选择“STARTTLS（连接后升级加密）”。
5. 执行 Alembic 迁移到最新 revision 后，再启动 API 与 worker。

候选人公开页由同一个前端站点提供。反向代理必须将 `/offer/` 返回前端页面，并将 `/api/public/v1/offers/` 转发到 API。项目 Nginx 模板已关闭这两类路径的访问日志，并添加 `no-store` 与安全响应头。

## HR 操作流程

1. 核对候选人邮箱。系统从简历中仅提取到一个有效邮箱时可直接用于发送；未提取到邮箱，或提取到多个邮箱无法确定主地址时，需由 HR 补充或选择并确认。
2. 在候选人详情的 Offer 页创建 Offer，设置回复截止日期并选择模板；特殊 Offer 需要填写原因。
3. 提交审批。审批完成后状态变为“待发送”，系统不会自动给候选人发送邮件。
4. HR 点击发送。成功响应仅表示邮件任务已入队；worker 发送成功后，Offer 才变为“已发送”。
5. 候选人通过邮件中的免登录链接查看 Offer PDF，并选择接受或拒绝。接受时必须填写预计到岗日期。
6. 候选人通过电话、微信或其他渠道回复时，HR 可点击“代候选人确认”，记录决定、沟通渠道、沟通时间和备注，并再次确认后提交。
7. 最终决定及来源会写入不可变记录。候选人确认邮件会按响应记录去重；负责 HR 会收到一次站内及飞书结果通知，代录人就是负责 HR 时不重复提醒自己。

## 链接与状态规则

- 公开链接只包含高熵 token，数据库只保存哈希；token 不进入邮件任务正文、数据库日志或 Nginx 访问日志。
- 一个 Offer 同时只能有一个有效发送 token。更新版本、撤回、发送失败或记录最终结果时会撤销旧 token。
- 过期、撤回、已被新版本替代的链接只显示对应终态，不能继续提交决定。
- 候选人与 HR 同时提交时，Offer 行锁和唯一约束只允许一个最终结果；另一方会看到冲突并刷新当前结果。
- 候选人公开页不加载员工会话，不显示 AI 评分、内部审批或面试反馈。

## 常见故障

### 无法发送 Offer

依次检查：Offer 是否审批完成、PDF 是否生成、截止日期是否仍有效、候选人是否有唯一可用邮箱或已确认邮箱、`OFFER_PUBLIC_BASE_URL` 是否配置、SMTP 配置测试是否通过。

### 邮件任务失败

在邮件记录中查看脱敏收件人和安全错误码。修复 SMTP 或候选人邮箱后，回到 Offer 页重新发送；不要重用已经失败发送所对应的旧候选人链接。

### 候选人确认后未收到确认邮件

业务结果不会因确认邮件配置失败而回滚。负责 HR 会看到邮件失败通知，可先核对最终 Offer 状态，再修复邮件配置并按企业流程人工确认。

### 候选人链接无效

确认是否已更新、撤回或重新发送 Offer，以及回复截止日期是否已过。不要从数据库或日志中尝试恢复 token；应由 HR 在有效 Offer 上重新发送。

## 发布与回滚

- 发布前备份 PostgreSQL 与 Offer PDF 对象，执行迁移，再滚动更新 API、worker 和前端。
- 验证 SMTP 测试、普通审批、特殊审批、发送、公开查看、候选人接受、HR 代拒绝、过期链接及失败重发。
- 已产生候选人响应后，不建议降级到不识别新响应字段的旧版本。紧急回滚应优先回滚应用镜像并保留数据库 revision，待兼容性确认后再处理 schema。
- 任何测试都不得使用真实候选人信息、生产 SMTP 密码或线上 token。
